## 0. 结论摘要

1. `docs/上机问题与代码修改记录.md` 里的事故根因（`reduction` 聚合初始化错位 +
   Active 分支漏 logical→motor 换算）**已正确修复**，配置、启动校验、站立目标复算均对得上。
2. EL05 协议实现与手册（type 1/2/17/18、0x700B、字节序、故障位）逐项一致，可以继续上机。
3. 但实机部署路径上仍有 **4 个 P0 级可靠性缺口**，其中两个与安全直接相关：
   - 命令文件超时检测因时钟基准混用而**永远不触发**；
   - IMU 文件冻结后 deploy **无法察觉**；
   - 一次瞬时 CAN 错误会**永久停发**所有指令；
   - 启动关键帧（运控模式/使能/力矩上限）**单发且不校验**。
4. 另有若干 P1/P2 配置陷阱与 sim2real 差异，最容易踩的是
   **`torque_threshold` 实际上是死参数**、**仿真 LowGain 仍是阶跃**、
   **仿真起立容差 2.0 rad vs 实机 0.25 rad**。
5. 当前最大不确定项仍是 **calf `reduction=1.5`** 与 **RL/RR 趴伏 `offset`** 未实测；
   它们同时影响观测、站立目标与力矩跳闸点。

## 2. 两份文档在讲什么

### 2.1 `上机问题与代码修改记录.md`

记录一次 `start_robot.sh low-gain` 使能瞬间机器人剧烈动作、扭断一个关节的事故。

根因链：

1. `JointCalibration` 增加 `reduction` 字段后，
   `defaultJointCalibration()` 兜底表仍是 4 字段写法，聚合初始化把 `lower`
   写进了 `reduction`，髋/大腿得到 `-0.785 / -0.26`。
2. 配置只为 calf 显式写 `reduction=1.5`，8 个髋/大腿沿用负值
   → 电机→关节斜率反向且左右不对称 → 后腿被驱到硬限位。
3. 安全监控用同一个错误映射计算跟踪误差，误认为"已到位"；
   力矩检查 `tau × reduction` 也被负值扭曲。
4. 附带 bug：ActivePC/ActiveRL 分支把逻辑角直接当电机角下发，漏 `motorPosition()`。

文档第二部分给出 10 项修改：兜底表、配置显式 reduction、启动校验、Active 分支修复、
LowGain 斜坡、CLI 开关、`limit_torque`、`watch_angles.py`、仿真同步、启动脚本。

### 2.2 `调试与上机操作手册.md`

当前链路与操作流程：

```
opendoge_deploy / 扫描工具 → SocketCAN can0-3（vcan）
  → usb2can_vcan_bridge.py（每个模块一个进程）
  → /dev/USB2CAN0/1 → DINGLAB USB2CAN V2.0 → EL05
```

覆盖：udev/设备节点、硬件检查、协议自检、单电机/单腿/整机三级调试、
IMU/手柄服务、构建与策略检查、上机顺序（dry → 悬挂 LowGain → damping → RL）、
急停优先级、常见故障表、安全红线。

## 4. 问题清单

### P0 — 实机安全 / 可靠性

#### P0-1 命令文件超时检测失效（时钟基准混用）

- **证据**：`deploy/src/main.cpp:34-38` 的 `nowSeconds()` 用 `std::chrono::steady_clock`
  （开机秒，约 `1e5` 量级）；`main.cpp:245-260` 却拿它与 `stat.st_mtime/st_ctime`
  （Unix 纪元秒，约 `1.7e9`）相减。`file_age_s` 恒为大负数，
  `command_timeout_s=0.5` 永远不会触发。
- **影响**：手柄桥进程若被 `SIGKILL`/崩溃且没来得及写中性命令，deploy 会**无限期保持
  最后的速度指令继续行走**。这正是该超时想防的场景。（`SIGTERM` 路径会写中性命令，
  所以通常停止 service 是安全的；风险在异常终止。）
- **现状规避**：现场必须有人守物理断电；不要只依赖"桥挂了会自动停车"。
- **备注**：`ImuSample::last_update_s` 同样只在 `readImuFile` 里被赋值，从未参与判断。

#### P0-2 IMU 文件冻结后无法察觉

- **证据**：
  - `deploy/src/runtime_io.cpp:273-323` 的 `readImuFile()` 只解析内容并置
    `imu.valid=true`，不比较文件 mtime；
  - `deploy/src/main.cpp:292-299` 的 `imu_invalid_count` 只在 `imu.valid==false` 时累加；
  - `hardware/imu/dm_imu_bridge.py:334-342` 在串口仍打开但不再来帧时，
    `state.ready()` 保持 true，桥接会持续写入**最后一帧旧数据**。
- **影响**：IMU 静默停流时，48 维观测里的 `projected_gravity` 与倒地检测都使用冻结值，
  且没有任何报警。robot 真倒了也可能检测不到。
- **现状规避**：上机前确认 `journalctl --user -u opendoge-imu` 无 timeout；
  测试期间人工观察姿态；不要把 IMU 正常当作理所当然。

#### P0-3 CAN 错误是故障锁存，且故障后停发所有帧

- **证据**：
  - `hardware/motor/el05_socketcan.cpp:296-300` 的 `fail()` 置 `ok_=false`，
    只有 `open()` 会复位；`drain()` 对任何 read 错误（包括未单独处理的 `EINTR`）
    都按致命错误处理；
  - `main.cpp:391-403` 在 `can.ok()==false` 时**不发送任何帧**；
  - `main.cpp:311-318` 的清故障路径又要求 `can.ok()`，因此软件无法恢复，只能重启进程。
- **影响**：一次瞬时 `ENOBUFS`（非阻塞 socket 缓冲满）或信号打断的 read，
  就会让机器人停在"最后一条控制帧"上，连阻尼帧都不再发送。
  一传三 + Python vcan 桥接的高负载场景更容易触发。
- **现状规避**：出现 `can_err` 增长或 `DampingFault` 后直接 Ctrl-C 并重启 deploy；
  重启后必须重新 clear_fault。

#### P0-4 启动关键帧单发且不校验电机应答

- **证据**：
  - `main.cpp:149-177` 对每个关节只发一次 `run_mode=0`、`ENABLE`（以及可选的
    `limit_torque`）；
  - `el05_socketcan.cpp:123-148` 的返回值只代表 `write()` 成功，不读回 `run_mode(0x7005)`；
  - `el05_socketcan.cpp:164-181` 的 `sendTorqueLimit()` 同样没有回读确认。
- **影响**：若某电机没切到运控模式（帧丢失或电机状态异常），type-1 控制帧会被忽略；
  它可能仍处于 PP/CSP 模式并按旧 `loc_ref` 动作。文档实测回包路径约 10% 丢失，
  TX 路径又没有确认机制，无法排除单帧丢失。
- **现状规避**：上机前用 `el05_motor_menu.py` 确认每个电机 `run_mode=0`；
  启动后看 `state=ready` 且 12 个 `recv=true`；有异常立刻断电。

### P1 — 配置陷阱 / 控制语义

#### P1-1 `torque_threshold` 在实机上不生效

- **证据**：`deploy/src/safety.cpp:121-124` 的优先级是
  `joint.max_torque > 0 ? joint.max_torque : config.torque_threshold`；
  而 `defaultJointCalibration()` 给所有关节 `max_torque=3.0`，conf 没有覆盖
  `joint.*.max_torque`。
- **影响**：在 conf 里把 `torque_threshold` 调到 2.0 不会改变跳闸点，实际仍按 3.0 判定。
  文档/conf 注释把它描述成可调旋钮，容易误导。
- **现状规避**：要改跳闸点，必须写 `joint.<name>.max_torque`；或先接受默认 3.0。

#### P1-2 sim2sim 的 LowGain 控制目标仍是阶跃

- **证据**：
  - C++ `controller.cpp:183-202` 所有非阻尼分支都用 `limited_target`；
  - Python `sim2sim/deploy_mujoco.py:1117-1121` 仍 `target_positions = DEFAULT_POS.copy()`，
    前面刚算出的 `limited_target` 没有参与控制。
- **影响**：仿真里从任意姿态切 LowGain 会瞬时扑向站立位，实机是 0.4 rad/s 爬升。
  `deploy_mujoco.py` 无法验证本次 LowGain bring-up 路径，也违反仓库
  "C++ 与 Python 控制回路必须同步"的约定。
- **现状规避**：LowGain 行为只以实机悬挂测试为准，不要用 sim 的低增益结果下结论。

#### P1-3 `Ready/EnteringPosition → ActiveRL` 直跳绕过起立保护

- **证据**：
  - `controller.cpp:98-105`：`active && rl_inference` 同时为真时，从 Ready 直接进 ActiveRL；
  - `controller.cpp:111-113`：EnteringPosition 斜坡中途按 X 也可直接切 ActiveRL。
  - 两条路都跳过 `pc_startup_max_deviation=0.25` 的位姿检查和剩余增益斜坡。
- **影响**：先按 A 再立刻按 X，可从任意姿态直接进入 RL 推理。
  仿真侧把直跳写成有意设计（`sim2sim/deploy_mujoco.py:8,43-44`），
  所以这不是回归 bug，而是**设计取舍在实机上的启动守卫缺口**。
- **现状规避**：严格按手册"先 A，等 2 s，再 X"操作；不要在机器人未站稳时按 X。

#### P1-4 运行期没有真正的"失能"路径，文档用词不准

- **证据**：
  - `sendStop` 只在启动（`main.cpp:163`）和清故障（`main.cpp:315`）调用；
  - 手柄 B/START/急停只改变 `active/estop`，让状态机进入阻尼
    （kp=0、kd=safe_kd），电机仍使能并持续收 type-1 帧（`opendoge_joystick.py:248-286`）；
  - deploy 退出只发 20 帧阻尼 burst 后 `close()`，不发 stop（`controller.cpp:39-54`）。
- **影响**：操作手册 §4.6/§4.7 的"按 B 失能 / START 切换使能"与代码语义不符；
  `--low-gain` 下 B 还完全无效（`main.cpp:238` 每轮 OR 回 true）。
  软件层面只能进阻尼，真正切断动力必须靠物理开关。
- **现状规避**：安全操作以物理断电为最终手段；不要把 B 当成电机失能。

#### P1-5 仿真的起立容差与实机不一致

- **证据**：`sim2sim/deploy_mujoco.py:217` 的 `pc_startup_max_deviation=2.0`
  （注释说明 MuJoCo 从 `REST_POSE` 起步需要大容差），
  实机 conf 是 `0.25`（`deploy/configs/opendoge_deploy.conf:35`）。
- **影响**：仿真可以从趴伏按 A 正常起立；实机同样操作会因偏差 >0.25 rad 直接
  DampingFault。这是首次上机最容易"仿真通过、实机失败"的点。
- **现状规避**：实机必须先悬挂到默认姿态 ±0.25 rad 内再按 A。

#### P1-6 calf `reduction=1.5` 仍未实测

- **证据**：`deploy/configs/opendoge_deploy.conf:65,86,107,128` 写死 1.5，
  文档 §待办 也标注"未实测"。
- **影响**：它同时影响 logical 角/速度（观测）、站立电机目标、
  以及 `safety.cpp:123` 的 `joint_torque = tau × reduction`。
  若真实比不是 1.5，跟踪误差、力矩跳闸点和最终姿态会同时偏。
- **现状规避**：用 `watch_angles.py` 手掰小腿约 0.2 rad，
  核对 `ΔmechPos / Δ关节角`；确认前不要落地/RL。

### P2 — 可靠性 / 可观测性

#### P2-1 `clear_fault` 脉冲过窄

- **证据**：`hardware/gamepad/opendoge_joystick.py:230-232` 的 `clear_fault`
  只保持一个桥接周期（默认约 10 ms）后自清零；deploy 每 5 ms 轮询一次。
- **影响**：正常情况能抓到；但现场日志出现过 `max_late_us≈107 ms`，
  RT 循环卡顿时会错过脉冲，表现为"按 A 无法清故障"，需要再按一次。
- **现状规避**：清故障失败时重复按 A；保留物理断电。

#### P2-2 `clampMotorTarget` 的保护范围被文档夸大

- **证据**：`controller.cpp:13-23` 的上下界用**同一份标定**换算
  （`motorPosition(lower/upper)`），而 `updateTargets` 已在逻辑空间 clamp 过一次。
- **影响**：若 `direction`/`offset`/`reduction` 本身配错，目标会落在"错误的允许区间"内，
  clamp 不能阻止关节被送往物理限位外。它只防"目标越出已配置限位"。
- **现状规避**：以启动校验 + 悬挂 + 低增益首测为准，不要因为"有 clamp"就跳过标定核对。

#### P2-3 `max_velocity` 是死配置

- **证据**：`types.hpp:108` 定义、`runtime_io.cpp:171` 解析，全仓库无使用点。
- **影响**：改它不会有任何效果；容易让人误以为有速度限幅。

#### P2-4 状态输出缺少目标/增益

- **证据**：`deploy/src/status.cpp:47-139` 的 JSON 只输出实测 `q/dq/tau/temp/fault`、
  指令速度和状态，不输出 `limited_target`、`kp`、`kd`。
- **影响**："目标是否在错误一侧"这类事故只能靠 `--dump-config` 的静态标定推断，
  无法从运行日志直接确认。

## 9. 2026-11-01 站立位 offset 复核（修改 11）

### 9.1 数学核对：通过

- 公式 `offset = mechPos_standing / reduction − direction × default` 与
  `types.hpp:224-227` 的 `motorPosition()` 逆运算一致。
- 用 conf 的新 offset 反算 12 个站立 raw，全部回到 `(0, 0.8, -1.6)`，与修改手册 §7 表一致。
- `--dump-config` 实测输出与 conf 完全一致；本次只改 conf，**不需要重新编译**
  （二进制仍是 2026-10-30 构建）。
- `direction` / `reduction` / `kp` / `kd` 与修改 11 声明一致，未变。

### 9.2 限位映射与手测物理范围的差异（上机注意）

把配置的 logical 限位用新 offset 换回 raw `mechPos`，与修改手册 §7 的手测范围比较：

| 关节 | 配置限位越出手测范围 |
|---|---|
| FL_hip | 下限多 **0.37 rad** |
| FR_hip | 上限多 **0.40 rad** |
| RL_hip | 下限多 **0.34 rad** |
| RR_hip | 上限多 **0.35 rad** |
| 四条 calf | 0.03–0.15 rad（FR_calf 两端各约 0.12–0.15） |
| 四条 thigh | 基本在范围内 |

手测范围可能受腿/机身干涉影响，不一定是硬限位；但结论是
**不能把 `clampMotorTarget` 当作硬限位保护**。首次 LowGain 让目标停在 default 附近；
进入 RL 前先逐关节确认限位，不要在第一次使能就把关节推到头。

### 9.3 配置来源陷阱（上机必查）

- `install/opendoge_deploy/share/opendoge_deploy/configs/opendoge_deploy.conf` 是
