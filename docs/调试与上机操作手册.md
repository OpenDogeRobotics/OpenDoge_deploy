# OpenDoge 调试与上机操作手册

> 适用硬件：赤乌（CHIWU）4×CAN + 3×RS485 控制板（单 USB-A，原生 SocketCAN
> `can0-can3`）+ 12× 灵足 EL05（经典 CAN，1 Mbps，29-bit 扩展帧）。
> 旧 DINGLAB/SOULDE USB2CAN V2.0 方案已归档到 `~/DingLab usb转can代码`，
> 见 [legacy/README.md](legacy/README.md)；当前**不要**安装 vcan/bridge。
>
> 本文所有命令默认在**仓库根目录**执行。仓库可能在：
> - x86 开发机：`~/RC/Lain_Code` 或 `~/orangepi_backup/Opendoge_code`
> - Orange Pi：`~/Opendoge_code` 或实际部署路径
>
> 请把命令里的 `<仓库根目录>`、`<SDK路径>` 换成你的实际路径。

## 0. 先读：当前链路与已知问题

### 0.1 链路结构

```
x86 / Orange Pi
   │  opendoge_deploy / scan_motors_readonly.py / el05_motor_menu.py
   │  AF_CAN can0-can3（原生 SocketCAN）
   ▼
赤乌（CHIWU）4×CAN 控制板（单 USB-A）
   │  板载 CAN1-CAN4 对应 can0-can3
   ▼
EL05 电机（4 条总线）
```

关键点：

- `scan_motors_readonly.py`、`el05_motor_menu.py`、`opendoge_deploy` **只认
  SocketCAN `canX`**；当前是内核驱动直接创建的原生 `can0-can3`。
- `opendoge-can.service` 负责等接口出现并设成 1 Mbps / fd off / UP。
- **没有** vcan，也**没有** `usb2can_vcan_bridge.py`；旧的桥接方案已归档。
- 手动无硬件测试仍可用 `scripts/setup_vcan.sh`，但生产路径不要用。

### 0.2 后端选择

当前只有一种后端：**Linux 原生 SocketCAN**（CHIWU/CANable/gs_usb 等）。
`opendoge-can.service` 的 `CAN_EXPECT_DRIVER` 默认 `gs_usb`；如果 CHIWU
实际驱动不同，在 `/etc/default/opendoge-can` 里改成实际驱动名，或设为
`auto` 只警告。

> 旧的 DingLab `vendor/native` 串口后端、`0xA8/0xA9` 帧、CRC8、
> `--allow-bad-crc` 等已随归档移除，不再适用于当前硬件。

## 1. 通用前置检查

### 1.1 USB 设备与 CAN 接口

```bash
# 1) USB 是否识别到 CHIWU 板
lsusb | grep -iE "can|chiwu|1483"

# 2) 原生 SocketCAN can0-can3 是否出现
ip -br link show | grep -E "can[0-9]"
for i in 0 1 2 3; do
  echo "can$i driver=$(basename $(readlink -f /sys/class/net/can$i/device/driver 2>/dev/null) 2>/dev/null)"
done

# 3) 接口详情：UP / bitrate 1000000 / 无 FD
ip -details link show can0
```

期望：`can0-can3` 都存在且 UP，驱动是 `gs_usb` 或实际 vendor 驱动，
没有 `vcan`。**当前方案不需要 `/dev/USB2CAN*`、不需要 udev usb_can.rules。**

> CHIWU 板枚举成 4 个独立的 `1d50:606f` gs_usb 设备。如果本次启动里
> can0-3 已被 vcan 用过，新接口会叫 **can4-can7**；
> `opendoge-can.service` 会先调用 `scripts/prepare_can_interfaces.sh`
> 按 USB 路径（1-3.6.1..4）改名为 can0-can3。可先预览：
> `bash scripts/prepare_can_interfaces.sh --dry-run`。

如果接口名顺序与板子 CAN1-CAN4 不一致，优先交换接线；必要时用
udev/systemd 按 USB 路径改名，最终必须 can0=FL … can3=RR。

### 1.2 硬件检查

- [ ] 一块赤乌（CHIWU）4×CAN + 3×RS485 板，单 USB-A 线
- [ ] 板子 CAN1→can0(FL)、CAN2→can1(FR)、CAN3→can2(RL)、CAN4→can3(RR)
      （以板子丝印和 `verify_can_mapping.py` 为准）
- [ ] CAN_H/CAN_L 不接反
- [ ] 120 Ω 终端只在总线两端（中间节点关闭）
- [ ] 板子 GND 与电机电源 GND 共地
- [ ] 电机独立电源已上电，电压/电流符合 EL05 手册
- [ ] USB Hub 带外部供电（尤其 Orange Pi）；单板可直插
- [ ] 有物理急停/断电开关

### 1.3 接口/协议自检

```bash
# 只检查接口/驱动/bitrate（不需要 root，也不读电机）
python3 scripts/verify_can_mapping.py --interfaces-only

# EL05 协议离线自检（无硬件）
python3 hardware/motor/protocol_selftest.py
```

期望：`--interfaces-only` 每个通道显示 `OK` 和驱动名；
`protocol_selftest.py` 全部通过。

## 2. 单电机调试

目标：确认 **一个模块 → 一路 CAN → 一个电机** 的链路、ID、供电、CAN 接线都正常。

**记得根据扫描结果连接信号线** 这里FR即右前腿对应的是can1

### 2.1 只读扫描（原生 SocketCAN）

前提：`opendoge-can.service` 已启动，`can0-can3` UP；没有 deploy 占用总线。

```bash
# 看单条总线上的所有 ID（含出厂 127）
sudo python3 hardware/motor/scan_motors_readonly.py --channel can0 --all-ids

# 看四条总线的映射
sudo python3 scripts/verify_can_mapping.py
```

哪一路有电机，就说明电机接在板子对应的 CAN 端子上。广播回复可能偶发丢帧，
扫描脚本会自动多轮补扫；仍缺电机时查 ID、接线、供电、120 Ω 和共地。

### 2.2 用菜单做单电机测试

前提：`canX` 已 UP；没有 deploy 占用总线。
```bash
sudo python3 hardware/motor/el05_motor_menu.py --channel can0 --ids 4
```

> `--ids` 必须写实际电机 ID。`can0` 默认只列出 1/2/3；电机是 4 就写 `--ids 4`。

菜单操作顺序：

| 菜单项 | 作用 | 建议 |
|--------|------|------|
| `2` | 读位置/速度 | 确认和扫描结果一致 |
| `10` | 读故障 `faultSta` | 必须为 0 |
| `7` | 切运控模式 `run_mode=0` | 当前已是可跳过 |
| `4` | 使能 | 电机保持力矩 |
| `8` | 小幅正弦运动 | **第一次实际运动用这个** |
| `5` | 停止 | 结束测试 |
| `9` | 机械置零 | ⚠️ 不要随便按 |

选择电机时的输入格式：

- 输入 **ID**，例如 `4`（不要输入 `04`）；
- 或关节名，例如 `FR_hip_joint`；
- 多个：`4,5`；
- 全部：`a`；
- 返回：`q`。

选项 8 的默认参数（直接回车使用）：

```
振幅 0.05 rad
频率 0.25 Hz
持续时间 4 s
Kp 5.0
Kd 0.2
```

安全要求：

- 电机必须固定或悬空，摆动范围内无遮挡；
- 第一次只用默认小振幅；
- 有异响/过流/过温立即 `5` 停止或断电。

代码：`hardware/motor/el05_motor_menu.py`

### 2.4 单电机常见问题

| 现象 | 检查 |
|------|------|
| 扫描“没有电机在线” | `canX` 是否存在且 UP？`ip -details link show canX`；是否用了 `sudo` |
| 有 TX 无 RX / 扫描无结果 | CAN_H/L、120 Ω、电机供电、通道接错、板子是否 1 Mbps |
| 菜单显示“无响应” | `canX` 是否 UP；deploy 是否占用总线；电机 ID/接线 |
| `Operation not permitted` | SocketCAN 工具需要 `sudo` 或 `CAP_NET_RAW` |
| 接口出现 `vcan` | 旧的 DingLab vcan/bridge 还在；停用并删除 vcan 接口 |

### 2.5 扫描标签 ≠ 物理安装位置（装电机前必读）

扫描输出里的名称（`FL_hip`、`FL_thigh`、`RR_hip`…）是按
**电机 ID → 项目映射表** 贴的标签，**不是从电机读到的物理位置**。

EL05 协议只上报 CAN ID、`mechPos`、`mechVel`、`run_mode`、`faultSta`、
`zero_sta`，没有“关节类型/安装位置”字段；电机本身不知道自己装在
hip、thigh 还是 calf。

例如 `can0` 期望是 `{1,2,3}`，实际扫描结果：

```
[can0] FL(左前) (OK) — 广播发现...
  发现 3 个电机: [1, 2, 10]
  [can0]         FL_hip  pos=-2.6889 ...
  [can0]       FL_thigh  pos=-2.8947 ...
  [can0]         RR_hip  pos=-2.0984 ...
```

这里 ID 10 实际装在 FL calf，但因为 `ID 10 → RR_hip` 是项目映射表的
固定名称，扫描就会显示 `RR_hip`，并按 ID 排在最后。
**不要用名称判断物理安装**；名称只表示“如果 ID 映射正确，它应该是这个关节”。

安装时的正确做法：

1. 扫描只用来确认：哪些 ID 在线、模式是否运控、`faultSta` 是否为 0、位置读数是否稳定；
2. 物理关节必须用 `el05_motor_menu.py` **逐个 jog** 确认（例如 ID 4 动的是不是 FR hip）；
3. 发现 ID 不在本组（如 can0 出现 10）时，视为“未通过”，不要使能；
4. 处理方式二选一：
   - 把电机拆回正确关节（保留原零位/offset/direction）；
   - 把 ID 改成当前物理关节对应的编号，并重新标零、核对方向/offset。

扫描无法自动识别物理安装；**不要**为了“排序好看”按 `mechPos` 重排结果，
那只会把误判藏起来。

## 3. 单腿调试

> **前提**：`opendoge-can.service` 已启动，对应的 `canX` 是原生 SocketCAN 且
> UP（1 Mbps、无 FD）。`el05_motor_menu.py` / `scan_motors_readonly.py`
> 只认 SocketCAN；接口没 UP 就一定是“无响应”。

目标：确认 **一条总线上的 3 个电机（hip/thigh/calf）** 都能独立运动，方向/零位没有明显错误。

以 can0（FL，ID 1/2/3）为例，其它腿替换通道和 ID：

| 腿 | 通道 | 电机 ID | 关节顺序 |
|----|------|---------|----------|
| FL 左前 | can0 | 1/2/3 | hip/thigh/calf |
| FR 右前 | can1 | 4/5/6 | hip/thigh/calf |
| RL 左后 | can2 | 7/8/9 | hip/thigh/calf |
| RR 右后 | can3 | 10/11/12 | hip/thigh/calf |

### 3.1 只读确认

```bash
sudo python3 hardware/motor/scan_motors_readonly.py --channel can0 --all-ids
```

期望只看到 1/2/3（或该腿对应的 3 个 ID），并且：

- 模式：运控
- `faultSta=0`
- 位置读数稳定

> 名称是按 ID 贴的标签，不代表物理关节；如果出现非本组 ID（如 can0 出现 10），
> 先按 2.5 节「扫描标签 ≠ 物理安装位置」处理。

如果看到别的腿的 ID，说明接口顺序/接线反了，先停止，不要使能。

### 3.2 逐关节小幅运动

```bash
sudo python3 hardware/motor/el05_motor_menu.py --channel can0 --ids 1,2,3
```

对每个电机分别执行：

1. `10` 读故障；
2. `4` 使能；
3. `8` 小幅运动（默认 0.05 rad）；
4. `5` 停止；
5. 换下一个 ID。

每次只动一个关节，确认：

- 物理上对应的是这条腿的这个关节；
- 正方向符合 URDF 约定（见 CLAUDE.md 的方向检测表）；
- 没有卡滞、异响、过流。

代码：`hardware/motor/el05_motor_menu.py`

### 3.3 方向和零位的判断

- 如果单关节运动方向与预期相反，先检查 `deploy/configs/opendoge_deploy.conf` 的 `joint.*.direction`，不要直接改机械。
- 如果 3 个关节在默认姿态附近位置读数与历史标定接近，说明零位/offset 仍然有效。
- **不要为了“保险”重新置零**。只有电机重装、重新编码器标定、机械结构变化时才按 `docs` 里的趴伏标零流程重做。

### 3.4 单腿能做什么、不能做什么

- 菜单的选项 8 一次只驱动一个电机；单腿的“同时站立”不适合用菜单硬凑。
- 单腿阶段的目标是**链路和方向验证**，不是整机站立。
- 整机 PD/LowGain 需要 4 条总线都接好，由 `deploy` 统一控制。

### 3.5 12 电机站立位重新置零（机身拆装后）

**适用**：机身/电机拆装、重新装机、怀疑零位漂移。脚本会
`COMM_SET_ZERO (0x06)` + `COMM_SAVE_PARAM (0x16)` 写 Flash。

前提（缺一不可）：

1. 机器人悬挂/可靠支撑，四条腿在默认站立位
   **hip=0.0、thigh=+0.8、calf=-1.6**（固件/URDF 约定）；
2. 已用 `verify_can_mapping.py` 和逐电机 jog/手推确认
   **物理腿→CAN 映射和 direction**（机身装反过尤其重要）；
3. `zero_sta (0x7029)` 应为 1；不确定时先跑 `--fix-zero-sta`（写完要断电重启）。

```bash
# 1) 只读预检：位置/故障/zero_sta/姿态
sudo python3 hardware/motor/zero_all_motors.py --dry-run

# 2) 如果 zero_sta=0：写入 1 并保存，然后断电重启电机
sudo python3 hardware/motor/zero_all_motors.py --fix-zero-sta

# 3) 真正置零（会二次确认）
sudo python3 hardware/motor/zero_all_motors.py --apply
```

脚本内部顺序：如果 `run_mode != 0`，先 stop → 写运控模式；然后
**不再 stop**，直接 `SET_ZERO` → `SAVE_PARAM` → 读回 `mechPos≈0`。
**不要**在运控模式和置零之间按菜单选项 5。

完成后：

```bash
# 给电机 24V 动力电断电重启（保持站立姿态不变）
sudo python3 hardware/motor/watch_angles.py --once
```

期望：12 个 raw `mechPos ≈ 0`，logical 为 `(0, 0.8, -1.6)`，
`faultSta=0`，没有 ±6.28 的 2π 跳变（尤其 FR_calf）。
通过后再跑低增益起立。

> offset 不需要改：站立置零 + 现有
> `offset = -direction*default`（hip 0、thigh ∓0.8、calf ±1.6）是一对。
> 只有重装后 `direction` 确实变了，才按同一公式改对应关节的 offset。
> 回滚：重新摆到正确站立位，再置零；不要恢复旧 offset（旧值属于另一个零点/分支）。

## 4. 整机上机调试

### 4.1 上机前硬件清单

- [ ] 一块赤乌（CHIWU）4×CAN + 3×RS485 板，单 USB-A
- [ ] 4 条总线接对，`can0-can3` 映射正确
- [ ] 12 个电机 ID 1-12，无重复
- [ ] 每条总线 120 Ω 终端（只在两端）
- [ ] 电机独立电源、急停/断电开关
- [ ] 机器人悬挂或固定在支架上（首次使能）
- [ ] IMU、Xbox 接收器已接到控制电脑
- [ ] USB Hub 外部供电

### 4.2 配置原生 CAN

```bash
# 一键安装/启动（root）
bash scripts/install_services.sh
sudo systemctl status opendoge-can

# 日常
sudo systemctl restart opendoge-can
ip -details link show can0     # UP / bitrate 1000000 / 无 FD
```

手动等价命令：

```bash
sudo modprobe gs_usb can can_raw
for i in 0 1 2 3; do
  sudo bash scripts/setup_can.sh can$i 1000000
done
```

> 如果 CHIWU 的实际内核驱动不是 `gs_usb`，在 `/etc/default/opendoge-can` 里
> 设置 `CAN_EXPECT_DRIVER=<驱动名>`，必要时设置 `CAN_MODULE=<模块名>`。
> `CAN_EXPECT_DRIVER=auto` 只警告不阻止。
>
> 当前**没有** vcan、没有桥接进程。如果 `ip -details` 看到 `vcan`，
> 说明旧 DingLab 单元还在：
> `sudo systemctl disable --now opendoge-vcan opendoge-usb2can0 opendoge-usb2can1`，
> 再 `sudo ip link delete can0` … 删掉 vcan 接口。

代码：`daemons/opendoge-can.service`、`scripts/setup_can.sh`

### 4.3 只读确认 12/12 和映射

```bash
sudo python3 hardware/motor/scan_motors_readonly.py \
  --timeout 0.5 --discovery-passes 3
sudo python3 scripts/verify_can_mapping.py
```

> USB-CAN 路径可能偶发丢帧。扫描会多轮补扫缺失 ID，参数读取也会重试；
> 如果仍随机缺电机，再查 120 Ω/共地/线缆、驱动和 USB 供电。

期望：

```
can0: 1,2,3
can1: 4,5,6
can2: 7,8,9
can3: 10,11,12
扫描完成: 12 个电机在线
```

`verify_can_mapping.py` 会拒绝：

- 意外 ID（接口接反）
- 缺失电机（除非 `--allow-missing`）
- 空总线

**映射不通过时不要使能。**

代码：`hardware/motor/scan_motors_readonly.py`、`scripts/verify_can_mapping.py`

### 4.4 IMU / 手柄 / 服务

`scripts/start_robot.sh` 的 `low-gain`、`damping`、`policy` 会先调用 `verify_all`，检查：

- CAN 接口 `can0-can3`（原生 SocketCAN，UP / 1 Mbps / 无 FD）
- `opendoge-xboxdrv`
- `opendoge-joystick`
- `opendoge-imu`

任一服务未运行，脚本会因为 `set -e` 直接退出，不会启动 deploy。

#### 4.4.1 安装服务

```bash
bash scripts/install_services.sh
```

这会：

- 安装/启用 `opendoge-can.service`（原生 can0-can3）
- 停用并清理旧的 `opendoge-vcan` / `opendoge-usb2can0/1` 单元（如存在）
- 安装 `opendoge-xboxdrv.service`
- 安装 IMU/手柄 user service（路径自动替换）

> 注意：
> - 不要用 `sudo bash scripts/install_services.sh`，否则 user service 会装到 root 名下。
> - 如果 CHIWU 驱动不是 `gs_usb`，先在 `/etc/default/opendoge-can` 设置
>   `CAN_EXPECT_DRIVER=<驱动名>`（或 `auto`）。
> - 旧 DingLab 代码已归档；不要再安装 `usb_can.rules` 或 vcan 服务。

#### 4.4.2 检查状态

```bash

#### 0) 无硬件 dry-run

```

#### 1) 悬挂 LowGain（第一次使能）

**前提**：`direction/offset` 已按实机重新标定（2026-11-01 站立位 offset 已写入配置），
`--dump-config` 确认无负 reduction、站立逻辑角为 `(0, 0.8, -1.6)`。

```bash

```

或手动控制首测增益：

```bash
./install/opendoge_deploy/bin/opendoge_deploy \
  --config deploy/configs/opendoge_deploy.conf \
  --real --enable --clear-fault --policy-backend none \
  --low-gain --kp 2 --kd 1.0
```

- **起立宽限期**：`standup_grace_s`（默认 6.5 s）是从进入 `StandingUp`/`LowGainTest`
  开始计的**时间窗**，不绑定状态，覆盖“斜坡 + 稳定段 + 交接淡入”，所以趴伏起立
  以及起身末尾 calf 弹一下都不会误报 fall；窗口结束后恢复，仍未站起会正常 fault。
  需要更长起立时间就调大 `standup_grace_s`（至少 >= duration + settle + handover）；
- **趴伏直接进 RL**：趴伏按 **A** 会先进 `standing_up`（从实测位姿 0.4 rad/s
  斜坡到站姿、不跑策略），斜坡结束后保持 `standup_settle_s`（默认 1 s）再进
  `active_pc`/`active_rl`；交接后 `standup_handover_s`（默认 1 s）内策略目标从
  默认姿态淡入，避免第一帧大动作让 calf 目标瞬跳。起立期间 tracking/torque
  仍生效，跟不动会 fault；
- 仍建议首次低增益悬挂/上支架；落地测试时保持急停；
- `--low-gain` 是部署级强制项，不依赖命令文件（手柄服务每 ~10 ms 覆盖命令文件）；
- 启动后确认 stdout：`state=low_gain_test`、`low_gain=1`、`can_rx ≈ 12 × 200`；
- 用 `sudo python3 hardware/motor/watch_angles.py --rate-hz 2` 看 12 关节 logical 角，
  应缓慢收敛到 `(0, 0.8, -1.6)`；髋轴到脚底约 **15.4 cm**；
- 观察方向、抖动、过流/过温；任一关节朝错误方向跑 → 立即急停/断电；
- 正常后 Ctrl-C（部署退出会发 `COMM_STOP` 失能电机）；**B 只回阻尼，不是失能**。

### 4.7 紧急停止

按优先级：

1. 手柄 **B**（退出位置控制，回到阻尼；**不切断电机输出**）；
2. 手柄 **btn11 急停**（锁存 estop，进 DampingFault；按 A 清除）；
3. **Ctrl-C** 停止 deploy（正常退出会发 `COMM_STOP` 失能电机）；
4. **菜单选项 5 (stop)** 对 12 个电机发 `COMM_STOP`；
5. **物理断电/急停**（切断电机动力电）。

注意：B 不是真正的失能——它只让部署回到阻尼（kp=0, kd=2），电机仍使能并有阻力。
如果 USB-CAN 适配器/驱动崩溃或 CAN 卡死，所有软件失能（`COMM_STOP`）都可能
不生效，**必须依赖物理断电**。`can_timeout_s=1.0` 是最后一道兜底。

### 4.9 高频记录（震荡/瞬态）

1 Hz 的 status/monitor 看不到 3–10 Hz 震荡。需要定位侧移/自转偶发震荡时，
在 deploy 运行中另开一个终端（**只读旁路 CAN，不发送任何帧**）：

```bash
# 默认 100 Hz，logs/highrate/highrate_<时间>.csv，最多保留 5 份
python3 hardware/motor/record_highrate.py --duration 120

# 看 10–20 Hz 冲击/振动时用 200 Hz（日志约翻倍）
python3 hardware/motor/record_highrate.py --rate-hz 200 --duration 60

# 只看终端，不写文件
python3 hardware/motor/record_highrate.py --no-csv
```

每行 = 一次采样，含 12 关节 `q/target/dq/tau/tau_j/temp/fault/status_age_ms/
target_age_ms` + IMU(`wx..gz`, `imu_age_ms`) + `cmd_vx/vy/yaw` + deploy `state`。
分析时画 `FL_hip/thigh/calf_q` 与 `_target`、`imu_wz`、`cmd_vy/cmd_yaw`，
对照 `flags` 里的 `TRACK/GAP/DQ/FAULT/IMU_STALE`，即可判断震荡频率、相位，
以及是 command 阶跃触发还是匀速时自发。

`target` 列依赖 SocketCAN 本地回环（deploy 的 type-1 发送帧会送到同接口的
其他 raw socket）；若一直 `NO_TARGET`，说明没抓到 type-1 帧，q/dq/tau 仍然有效。
CAN raw socket 在部分系统需要 root/CAP_NET_RAW，权限不足时用 sudo 运行。

## 6. 常见故障排查

| 现象 | 优先检查 |
|------|----------|
| `scan_motors_readonly.py` 显示“不可用/没有电机” | `ip -details link show canX` 是否 UP；是否 `sudo`；驱动/接线/ID |
| CAN 有 TX 无 RX | CAN_H/L、120 Ω（只两端）、电机供电、通道接错、板子 1 Mbps |
| 接口显示 `vcan` | 旧 DingLab 单元还在：`sudo systemctl disable --now opendoge-vcan opendoge-usb2can0 opendoge-usb2can1`，再删除 vcan 接口 |
| `verify_can_mapping.py --interfaces-only` 报 driver/bitrate | 看实际驱动；`/etc/default/opendoge-can` 的 `CAN_EXPECT_DRIVER`/`CAN_MODULE`；`setup_can.sh` |
| `start_robot.sh` 直接退出 | `verify_all` 失败：IMU/手柄/xboxdrv 服务未运行 |
| IMU bridge 反复失败 `Permission denied` | 安装 `hardware/imu/99-opendoge-imu.rules` 或加入 `dialout`；重载 udev/重插 IMU |
| 接收器显示 `3537:2106` | 该模式不创建 js0；拔插/切换回 `3537:1041` |
| Zikway `3537:1041` 按键不对 | 原生 js0 按钮编号与 xboxdrv 不同；先 `jstest /dev/input/js0` 再传 `--btn-*` |
| 电机方向相反 | 检查 `direction`，不要直接改机械 |
| 默认姿态明显不对 | 检查 `offset`；不要随意重新置零 |
| 温度/力矩/跟踪报警 | 降低增益/频率，检查机械卡滞、供电、CAN 丢帧 |
| 一使能就 `fall detected: gravity.z=-0.99 > -0.3`? | 旧版 safety.cpp fall 符号写反；当前代码已修为 `gz > -threshold`，需重新 build |
| `feedback timeout` 偶发 | USB-CAN burst/线束；先对比 `control_hz=100/200`（当前 200）；deploy 运行时不要开 `watch_angles`（用 `--from-status`）；看监控 `age_ms`/`STALE`；仍频繁查 120Ω/共地/电机供电与驱动 |
| 广播只发现一个/部分电机 | 扫描已自动多轮补扫；仍随机缺失查 120Ω/共地/线缆/驱动 |
| 随机缺电机、`发现但无法读取参数` | USB-CAN 丢帧；查线缆/接头/供电，必要时提高 `--discovery-passes`/`--timeout` |
| 扫描出现非本组 ID（如 can0 出现 10） | 标签只是 ID 映射，不代表物理安装；用 jog 确认关节，不要按名称判断（见 2.5） |
| `lsusb` 看不到 CHIWU 板 | USB 线/口/供电；`dmesg`；必要时换 USB-A 线或直插 |
| `Operation not permitted` | SocketCAN 工具需要 root/CAP_NET_RAW |
| 退出 deploy 后电机仍有阻力 | 电机仍使能并执行最后的 `kd=2.0` 阻尼。新二进制 Ctrl-C 会发 `COMM_STOP`；旧二进制或 `--keep-enabled` 不会。用菜单选项 5 或断电松开 |
| 按 B 后电机还是硬 | B 只退出位置控制回到阻尼，**不切断电机输出**。真正失能：Ctrl-C（新二进制）/ 菜单选项 5 / 物理断电 |
| `watch_angles.py: error: unrecognized arguments: --sequential` | 旧脚本；当前默认就是顺序读，直接 `--rate-hz 2`；更新后 `--sequential` 是兼容别名 |
| 菜单选项 8 输入 `1` 却动了 thigh | 旧版选择器把数值先当 0-based 索引；现在**数值=ID**，列表序号用 `#N`。主菜单选项 2/4/5/7 不受影响 |
| `low_gain=0` / 脚本进了却没低增益 | 命令文件被手柄服务覆盖；用 `--low-gain` 部署级强制项 |
| `fault_reason="cannot open /tmp/opendoge_command.state"` | 旧版把缺失命令文件当故障；当前版改为“中性命令 + 5 s 警告”，不再 DampingFault。启动手柄服务或建文件即可；文件存在但格式错仍会故障 |
| `can_rx` 掉到 0 / 频繁 feedback timeout | 查 `can0-3` 是否仍 UP、USB 是否重新枚举、终端电阻（只两端 120Ω）、共地、电机供电；保持 `control_hz=100` |
| Ctrl-C 后重启，狗子自己站起来 | 手柄 active 跨部署重启锁存；当前版默认要求先释放一次 active（B/START），或启动前按 B；`--allow-latched-activation` 恢复旧行为 |
| 遥控响应慢 / 角度变化大 | 还在 ActivePC，3 rad/s rate limiter 限速；按 X 进 ActiveRL；角度变化大是策略步态本身 |
| RL 轻推抬不起腿 / 大动作大幅踏步或倒地 | 小腿 kp/kd 必须按 `1/r²` 换算到 EL05 电机侧（当前代码已做：kp 5.33、kd 0.22）；`lin_vel_source` 试 `zero`；动态确认 IMU 轴向；calf `max_torque=6`；仍触发倒地再放宽 fall 阈值 |
| 垫在箱子/地上就 `fall detected` | 当前版倒地检测只在主动控制/起立状态生效，Ready/阻尼不再因姿态 fault；若主动控制时报 `gravity.z≈+1`，说明机身真的倒置或 IMU 装反，先 `cat /tmp/opendoge_imu.state` 确认竖直时 `gz≈-1` |
| deploy 反馈成功率不如 scan 脚本 | scan 是低频、长超时、无并发运控；deploy 100 Hz ×12 同时收发。先 `verify_can_mapping.py` 确认 12/12；对比 `control_hz` 50/100；补扫只是缓解 |
| 读角度感觉延迟 | `watch_angles` 的 sequential+retries 在丢包时一轮 8–10 s；deploy 运行时用 `--from-status /tmp/opendoge_status.json`，不要用 CAN 读 |
| 遥控延迟高 / 命令滞后 | 旧版 joystick bridge 每写一次就 `fsync` 到 ext4，且 IMU 桥接 1 kHz 写；当前版已去掉 fsync、IMU 限 200 Hz。改完要 `systemctl --user restart opendoge-imu opendoge-joystick`；也可把 IPC 文件放 `/dev/shm` |
| RL 一站就自己动 / 往一个方向偏 | 先验证 IMU 轴向/符号：静止 `gz≈-1`；绕 Z 转看 `wz`、绕 Y 看 `wy`、绕 X 看 `wx`。不对就给 `opendoge-imu.service` 加 `--axis-map/--axis-signs`；也试 `lin_vel_source=zero`。注意 policy 模式下按 A 就已经在跑策略 |
| 小 yaw 指令身体绕 z 晃、大指令混乱 | 优先查 IMU：从上方看逆时针偏航时 `wz` 必须为正；**低头 `gx>0`**、抬头 `gx<0`、右侧向下 `gy<0`。再查 RL_thigh/RL_calf 的 `direction/零位/机械`。用 `python3 hardware/motor/monitor_status.py --rate-hz 2` 看 `OUT/TRACK/DQ/TAU/FAULT`（默认自动写 `logs/monitor_status/`，最多保留 5 份；只读终端加 `--no-csv`）；先 0 速度站稳再逐步给 vx/vy/yaw |
| RL 行走震荡 → 原地大幅踏步 → 电机掉线 | 先看 `ip -details -statistics link show can0`：出现 `ERROR-PASSIVE`/`error-pass`/`bus-errors` 就是 CAN 物理层（120Ω 只两端、共地、CHIWU 外部供电、电机动力线与 CAN 分开）；12 关节同时 `age_ms` 变大不是单根线。IMU 是独立串口，不会“打爆”CAN |
| 一条腿丢包后，其他腿没有立即阻尼、继续按最后目标动 | 旧版控制块在第一个 `sendMotion` 失败处 `break`，且 `can.ok()` 被永久置 false，导致 12 个关节都不再收到阻尼帧，健康腿保持最后 RL 目标直到 1 s canTimeout。当前版已改为每个 tick 尝试发全部 12 个关节（修改 53）；使用新二进制。若四路都失败，是 USB/供电全局问题 |
| 想让狗子对陀螺仪反应小一点 | 先确认 `wz` 符号和量程（CCW → `wz>0`；转一圈 `∫wz dt≈2π`）。确认无误后，可在 `opendoge-imu.service` 的 ExecStart 加 `--gyro-lowpass-hz 50`（40–60 Hz 可选）做 A/B；**不要**整体缩小角速度，那会破坏策略速度反馈 |
| 想同时看目标/实际/异常标记 | `python3 hardware/motor/monitor_status.py`（只读 `/tmp/opendoge_status.json`，不占 CAN）；默认每次运行自动写 `logs/monitor_status/monitor_status_<时间>.csv`，最多保留 5 份（`--keep` 改数量，`--no-csv` 只打印终端，`--csv PATH` 仍是旧的追加行为，`--log-dir` 改目录）。新版 JSON 还带 `pos/vel/status_age_ms`、`max_gap_ms`、`rx_ratio`、`can_buses`、`imu_age_ms`，monitor 会显示 `STALE_STATUS/GAP/FB_RATIO`、IMU age 和 CAN 控制器状态（`--status-stale-ms/--max-gap-ms/--min-rx-ratio/--imu-stale-ms`）。1 Hz 快照可能漏掉几十 ms 瞬态；`--rate-hz > 1` 只是重复快照，CSV 会跳过未变化的行 |
| 想看 100/200 Hz 的 q/target/dq/tau + IMU + command（震荡/瞬态） | `python3 hardware/motor/record_highrate.py`（只读旁路 CAN，另开 4 个 raw socket，不碰 deploy 实时线程）；默认 `logs/highrate/`、100 Hz、最多 5 份（`--rate-hz 200` 看高频，`--no-csv` 只看终端，`--csv PATH` 追加不轮转）。`target` 需要 CAN 本地回环；一直 `NO_TARGET` 时 q/dq/tau 仍有效 |
| 想看策略实际用了多旧的样本 | `cat /tmp/opendoge_status.json` 看 `obs_imu_age_ms/obs_joint_age_ms`（推理前刷新后的观测年龄，正常应 ~0–5 ms）；`imu_age_ms` 仍是 200 Hz 安全轮询样本的年龄 |
| damping_fault 时监控报 OUT/TRACK | 正常，不是新的超限故障。阻尼状态下 JSON 的 `target` 只是默认站姿占位值，电机实际在按实测位置阻尼；新版监控只在主动控制状态检查 OUT/TRACK。优先看 `STALE`（反馈年龄）、`FAULT`、`TAU` |
| 某个关节反馈年龄大 / 偶发 timeout | JSON `age_ms` 和监控 `STALE` 会指出具体关节；对应总线的丢包问题（线缆/接头/振动），先修物理链路，不要只调大 `state_timeout_s` |
| Ctrl-C 后个别电机仍有阻尼、不停 | 它的 COMM_STOP 可能随丢包一起丢了（SocketCAN 写入成功≠电机收到）。新版 deploy 会检查反馈新鲜度并打印 `cannot confirm disable on ...`；根治是 `can_timeout_s=1.0`（deploy 启动自动写 0x7028），或手动 `el05_set_can_timeout.py --value 20000 --apply`。仍卡住时用菜单选项 5 或断电 |
| `start_robot` 报 `canX does not exist / DOWN / bitrate` | `lsusb` 看 CHIWU；`ip -br link show`；`systemctl status opendoge-can`；`journalctl -u opendoge-can -n 40`；`readlink /sys/class/net/can0/device/driver` |
| 给电机断电后 can0-3 DOWN；restart 报 `RTNETLINK ... Connection timed out`；内核 `gs_usb ... Couldn't start device (err=-110)` | CHIWU 板/Hub 被电机电源一起复位。恢复板子 24V，`sudo scripts/reset_can_usb.sh`；仍不行就彻底拔 USB/断电 5–10 s 再上电。长期方案：CHIWU 的 24V 不要和电机动力电共开关 |
| `opendoge-can` 报 `expected driver ..., got ...` | 实际驱动不是 gs_usb：在 `/etc/default/opendoge-can` 设 `CAN_EXPECT_DRIVER=<驱动名>` 或 `auto`，`CAN_MODULE=<模块名>` |
| 接口顺序不对（can0 不是 FL） | 优先交换 4 条 CAN 接线；必要时用 udev/systemd 按 USB 路径改名；必须 `verify_can_mapping.py` 通过 |
| 开机日志出现 `ordering cycle ... can ... start deleted` | 已安装的旧 `opendoge-vcan.service` 还带 `After=multi-user.target`：`bash scripts/install_services.sh` 重装/清理，或手动改 unit 后 `daemon-reload` |
| realtime / 绑核需要每次手动吗 | 不需要：`start_robot.sh` 已默认 `REALTIME_ARGS="--realtime --cpu 0"`；`sudo setcap cap_sys_nice+ep install/opendoge_deploy/bin/opendoge_deploy` 一次即可，但**每次重新编译后会丢失**。CAN/IMU/手柄单元已绑 CPU 2-3/4-5/6-7（需重装）。临时关闭：`REALTIME_ARGS="" bash scripts/start_robot.sh damping` |

## 7. 安全红线

1. 第一次使能必须悬挂/固定，不能直接落地。
2. 不要随意使用菜单选项 9（机械置零）；它会立即写 Flash 并改变标定。
3. 不要跳过 LowGain 直接 RL。
4. 不要只依赖软件失能；必须能物理切断电机电源。
   `B` 只是回阻尼，不是失能；软件失能是 `COMM_STOP`（Ctrl-C 正常退出 / 菜单选项 5）。
   USB-CAN 适配器/驱动卡死时，`COMM_STOP` 也可能送不到，最终必须断电；
   `can_timeout_s=1.0` 是兜底，不是替代品。
5. 接口映射未通过 `verify_can_mapping.py` 前，不要使能。
6. **不要**同时运行 vcan/旧 DingLab bridge 和原生 can0-3（同名接口冲突）；
   生产只保留 `opendoge-can.service`。
7. vcan 只用于离线 dry-run，不是生产级 CAN；生产用 CHIWU 原生 can0-3。
