## 第一部分：问题记录与分析

### 1. LowGain“疯狗”/ 关节被别断（根因，最高优先级）

#### 现象

- 机器人趴伏在地面，执行 `start_robot.sh low-gain` 后使能瞬间剧烈动作。
- 小腿伸直到最大角度；髋关节向身体正下方几何中心投影处旋转。
- 一个关节被踢断。
- 日志：`state=damping_fault`、`fault="FL_hip_joint: feedback timeout"`、
  `can_tx≈12000/s`、`can_rx` 从 712 掉到 0、`low_gain=0`。

#### 根因

`JointCalibration` 的字段顺序是：

```cpp
direction, offset, reduction, lower, upper, max_position_step, ...
```

但 `defaultJointCalibration()` 的兜底表仍是**加入 `reduction` 之前的 4 字段写法**：

```cpp
{1.0, 0.0, -0.785, 0.26}   // 原意是 {dir, offset, lower, upper}
```

聚合初始化按位置赋值，于是变成：

```text
direction = 1.0
offset    = 0.0
reduction = -0.785   ← 原本想写 lower
lower     = 0.26
```

配置里只为小腿写了 `reduction=1.5`；8 个髋/大腿关节没有 `reduction` 键，
于是保留了负的兜底值。实际生效：

| 关节 | 生效 reduction |
|------|----------------|
| FL/RL hip、全部 thigh | **-0.785** |
| FR/RR hip | **-0.26** |
| 四条 calf | 1.5（配置覆盖，正常） |

负 reduction 会**反转电机→关节斜率**，且左右不对称。按站立目标
`default_pos = (0, 0.8, -1.6)` 计算，实际物理角为：

| 关节 | 目标 L | 实际物理角 | 限位 | 结果 |
|------|--------|-----------|------|------|
| RL hip | 0 | **+0.466** | [-0.785, 0.26] | 顶穿上限 |
| RR hip | 0 | **-0.329** | [-0.26, 0.785] | 顶穿下限 |
| RL/RR thigh | 0.8 | **+1.399** | [-0.785, 1.134] | 顶穿上限 |
| FL/FR hip | 0 | +0.107 / -0.076 | 在范围内 | 角度错 |
| FL/FR thigh | 0.8 | 0.731 | 在范围内 | 角度错 |
| 四条 calf | -1.6 | 由真实机械比决定 | [-2.68,-1.04] | 目标本身正确 |

后腿髋/大腿被直接驱到硬限位，与现场“髋往几何中心转、关节被别断”完全吻合。

#### 为什么安全监控没拦住

- `logicalPosition()` 使用**同一个错误 reduction**，所以
  `logicalPosition(实际电机位置) == 目标 L`；
  跟踪误差、状态输出、安全监控都认为“已到位”。
- 力矩保护 `joint_torque = motor_torque × reduction`
  （`deploy/src/safety.cpp:121-123`）被负值扭曲：
  FR/RR 髋的 3 N·m 阈值实际变成约 11.5 N·m。

#### 附带发现的第二个 bug

`computeMotorCommands()` 的 **ActivePC/ActiveRL 分支**把
`limited_target[i]`（**逻辑角**）直接当作 `MotorState.q`（**电机角**）下发，
漏了 `motorPosition()` 转换：

```cpp
// 修改前（Active 分支）
double target = limited_target[i];      // logical
commands[i] = {target, 0, 0, kp, kd};   // 当成 motor 发了
```

只有 `EnteringPosition` 和 `LowGain` 分支做了转换。这会让位置控制/RL
在 `direction=-1`、`offset≠0`、`reduction≠1` 的关节上完全走错。

### 2. 一传三 CAN 总线

**结论：不会串控，这是 CAN 的正常拓扑。**

- 三个电机并联在同一对 CANH/CANL 上是标准多点总线；所有节点都能收到所有帧，
  但每个 EL05 只执行 29 位 ID 中 **bit7~0 == 自己 CAN ID** 的帧
  （通信类型 1 的 bit7~0 = 目标电机 ID）。
- 只要 **ID 唯一**，1 号电机的指令不会被 2/3 号执行。

需要关注的风险（不是串控）：

| 风险 | 说明 | 处理 |
|------|------|------|
| ID 重复 | 出厂默认 127；重复 ID 会多电机同时执行、回包无法区分 | `verify_can_mapping.py` 校验 can0={1,2,3} … |
| 总线负载 | 3 电机 × 1000 Hz 指令 + 3 × 回包 ≈ 6000 帧/s；29 位扩展帧约 130–150 bit，1 Mbps 利用率 ~80–95% | 一传三建议 `control_hz=200`（~15–20%） |
| 终端电阻 | 一条总线只在两个物理末端接 120 Ω；三个都打开会并联成 ~40 Ω | 中间电机终端关掉 |
| 极性/共地 | CANH/CANL 不可反；电机电源地与 USB2CAN 共地 | 检查线序、加共地线 |
| 适配器 FD | EL05 要求经典 CAN 1 Mbps | 不要开 FD；`verify_can` 会拒绝 FD |

项目现有保护机制：

- 唯一 ID 映射 `defaultJointMap()`；
- `El05SocketCan::open()` 拒绝**映射内**重复 ID
  （`hardware/motor/el05_socketcan.cpp:58-76`）；
- `scan_motors_readonly.py` 发现 ID、`verify_can_mapping.py` 拒绝意外/缺失 ID；
- 回包按 `data2 & 0xFF` 归属电机（`el05_socketcan.cpp:239`）；
- `state_timeout_s` 反馈超时、逐电机 `fault`/`faultSta`/温度/力矩监控；
- `sendStop`、物理急停。

**没有**电气级“单电机隔离”——CAN 靠地址字段，这是设计使然。

### 2b. 手动桥接报“/dev/USB2CAN0 已被其他进程打开”

**现象**：先在终端手动启动桥接，关掉后再启动，报
`/dev/USB2CAN0 已被其他进程打开`；与此同时 `watch_angles.py` 仍能读到电机。

**原因**：

- `NativeUsb2Can.__init__` 对 `/dev/USB2CAN*` 做
  `fcntl.flock(LOCK_EX | LOCK_NB)`，同一个设备只允许一个进程打开。
- `opendoge-usb2can0/1.service` 是 `Restart=always` 的 systemd 服务。实测：
  `systemctl is-active opendoge-usb2can0 opendoge-usb2can1` 均为 `active`，
  `pgrep -af usb2can_vcan_bridge.py` 显示两个 systemd 进程
  （PID 105398 / 105400）正持有 `/dev/USB2CAN0` / `/dev/USB2CAN1`。
- 用户关掉的只是**终端里的手动桥接**；systemd 桥接一直活着，所以：
  1. 手动桥接再次启动 → flock 失败；
  2. `watch_angles.py` 仍能读到电机 → 因为它在用 SocketCAN `canX`，
     systemd 桥接一直在转发。

**结论**：`watch_angles.py` **不打开** `/dev/USB2CAN*`，不可能“代替桥接”。
没有桥接时它不会报设备错误，只会收到 0 个回包（全 n/a）。

**处理**：

```bash
# 查看谁在跑
systemctl is-active opendoge-usb2can0 opendoge-usb2can1
pgrep -af usb2can_vcan_bridge.py

# 要手动跑桥接，先停 systemd 的
sudo systemctl stop opendoge-usb2can0 opendoge-usb2can1
# 跑完再恢复
sudo systemctl start opendoge-usb2can0 opendoge-usb2can1
```

**回包丢失证据**：本次检查时 `opendoge-usb2can0` 的桥接统计是

```text
[bridge] can->usb=30  usb->can=27  tx_ok=30 tx_fail=0 ret={17: 30}
```

30 个请求只有 27 个回包 → USB2CAN/EL05 串口路径确实会丢约 10% 的回包。
这就是 `watch_angles.py` 需要“重试 + 多轮补扫”的原因。

### 3. 菜单逐组读角度效率低

现象：`el05_motor_menu.py` 每次读角度要输入一组 ID，掰完再按 2 看，无法连续观察。

结论：可以实现一个类似 `watch` 的只读脚本。已新增

### 4. CAN 1000 Hz × 12 电机与 Python vcan 桥接瓶颈

- 部署 `control_hz=1000`，12 路运控帧 ≈ 12,000 帧/s。
- 当前链路是单线程 Python USB2CAN→vcan 桥接，其代码注释写明
  “12 电机 × 200 Hz 可能成为瓶颈”
  （`hardware/motor/usb2can_vcan_bridge.py:27-30`）。
- 日志 `can_rx` 712→0、`max_late_us` 出现 107 ms，吻合。
- 没有反馈时部署会进 `DampingFault`，安全监控也失去意义。

处理：一传三 + vcan 场景把 `control_hz` 降到 200；换回 CANable 原生
can0-3 后再考虑 1000。

### 5. low-gain 从趴伏起立被三重保护打断

即使 reduction 正确，当前代码从趴伏做 LowGain 仍会被打断：

| 保护 | 阈值 | 趴伏→站立误差 | 结果 |
|------|------|--------------|------|
| 跟踪误差 | 0.5 rad / 0.3 s | calf 0.66–1.03 rad | 0.3 s 后 DampingFault |
| IMU 倒地 | `gz > -0.3` / 0.3 s | 趴伏 `gz≈0` | 0.3 s 后 DampingFault |
| 力矩 | 3.0 N·m / 0.5 s | 低增益 3.7 N·m | 0.5 s 后 DampingFault |

结论：当前流程事实上只支持“悬挂在站立位姿附近”的首次使能。
本次已把 LowGain 目标改成**从实测位姿缓慢爬升**（0.4 rad/s），
跟踪误差不会在起步瞬间超限；但**趴伏时 IMU 倒地检测仍会触发**，
所以首次测试仍应悬挂。

### 6. 力矩相关：到底在哪里改

部署**从不发前馈力矩**（`tau` 恒为 0），所有力矩来自 EL05 内部 PD：

```text
τ = Kp·(q_des − q) + Kd·(dq_des − dq)
```

| 目的 | 位置 | 说明 |
|------|------|------|
| 降低 PD 刚度/阻尼 | `deploy/configs/opendoge_deploy.conf` 的 `kp` / `kd` / `safe_kd` | 全局 |
| 逐关节上限 | 同文件 `joint.<name>.max_kp` / `max_kd` | 代码会 clamp |
| **硬件力矩硬上限** | EL05 `0x700B limit_torque`（0–6 N·m） | 本次新增 `torque_limit_nm`，启动时写入 |
| 电流/速度限制 | `0x7018 limit_cur`、`0x7017 limit_spd` | 未接入，可按需扩展 |
| 安全跳闸阈值 | `max_torque`（默认 3.0） | **只是报警阈值，不是限幅器** |

**关键结论**：只降 `kp` 不能解决本次别断——目标仍被算到限位外，
只是更慢地顶进去。必须先修 reduction，再加 motor 目标硬 clamp 和
`limit_torque`。

### 7. 重新装机后的标定复核（2026-10-30）

用户重新装机后手转 12 个电机，实测 raw `mechPos`（趴伏/完全收回）与物理范围：

| 关节 | 趴伏/收回 mechPos | 物理范围 |
|------|------------------|----------|
| FL_hip | -2.70 | [-3.30, -2.40] |
| FL_thigh | -0.30 | [-1.35, 0.77] |
| FL_calf | -1.50（完全收回） | [-1.50, 0.97] |
| FR_hip | +3.02 | [2.39, 3.57] |
| FR_thigh | +2.21 | [1.02, 3.36] |
| FR_calf | -2.44（完全收回） | [-4.50, -2.44] |
| RL_hip | +1.70 | [1.30, 2.50] |
| RL_thigh | +0.04 | [-1.10, 2.58] |
| RL_calf | -1.90（完全收回） | [-1.90, 0.52] |
| RR_hip | -0.90 | [-1.46, -0.26] |
| RR_thigh | +0.09 | [-0.94, 1.36] |
| RR_calf | +1.72（完全收回） | [-0.80, 1.72] |

**结论：**

1. **旧 offset 全部过期。** 旧 offset 假设趴伏时 `mechPos≈0`；实测髋和 FL/FR
   大腿的趴伏 mechPos 偏 0.3–3.0 rad。按旧配置，FR_calf 的站立目标 mechPos
   为 -0.99，而实测物理范围是 [-4.50,-2.44]——目标在范围外，使能会顶限位。
2. **calf `reduction=1.5` 确认。** 四条 calf 的 mechPos 宽度 ÷1.5 =
   1.37–1.68 rad，配置的逻辑范围宽度是 1.64 rad；FL/RL/RR 几乎完全吻合。
3. **calf 方向确认。** “完全收回→伸展”的 mechPos 方向：FL/RL 增大、FR/RR 减小，
   与配置的 `direction=+1/-1` 一致。
4. **方向复核完成：12 个 `direction` 与当前配置全部一致，无需修改。**
   用户推关节时对部分关节推的是 URDF 负方向：FR/RR hip（URDF+ 是向内）、
   四条 thigh（URDF+ 是向前，用户推的是向后）。映射到 URDF+ 后：
   FL_hip -1、FR_hip -1、RL_hip +1、RR_hip +1；
   FL_thigh +1、FR_thigh -1、RL_thigh +1、RR_thigh -1；
   FL/RL calf +1、FR/RR calf -1。全部与配置一致。
   之前“RL_thigh 疑似 -1”的推断错误：0.32–0.6 是向前（URDF+）方向的量，
   趴伏→站立实际是向后转，mechPos 应下降约 0.336，落到约 -0.296。
5. **下一步**：吊起做站立位标定（`hip=0, thigh=0.8, calf=-1.6`），
   读 12 个 mechPos 重算 offset。站立位精度 ±3–5° 即可。

**站立位实测 mechPos（2026-11-01）：**

| 关节 | mechPos | 关节 | mechPos |
|------|---------|------|---------|
| FL_hip | -2.8149 | FR_hip | +2.7792 |
| FL_thigh | +0.3328 | FR_thigh | +1.8275 |
| FL_calf | +0.0703 | FR_calf | **+2.4427** |
| RL_hip | +1.7456 | RR_hip | -0.6954 |
| RL_thigh | +0.3540 | RR_thigh | -0.1705 |
| RL_calf | -0.4933 | RR_calf | +0.2672 |

按 `offset = mechPos/reduction − direction×default` 算出的软件 offset：

| 关节 | offset | 关节 | offset |
|------|--------|------|--------|
| FL_hip | -2.8149 | FR_hip | +2.7792 |
| FL_thigh | -0.4672 | FR_thigh | +2.6275 |
| FL_calf | +1.6469 | FR_calf | **+0.0285（有 2π 问题）** |
| RL_hip | +1.7456 | RR_hip | -0.6954 |
| RL_thigh | -0.4460 | RR_thigh | +0.6295 |
| RL_calf | +1.2711 | RR_calf | -1.4219 |

6. **FR_calf 多圈计数差了 2π。** 站立 raw +2.4427 超出其物理范围
   [-4.50, -2.44]；raw − 2π = -3.8405 落在范围内。
   用 raw 算的 offset +0.0285 只在**本次上电**自洽（目标也是 +2.4427）；
   一旦多圈计数变化，logical 会跳 2π/1.5 ≈ 4.19 rad。
7. **掉电稳定性已验证**：用户断电重启后重读，12 个 mechPos 最大变化 0.03 rad，
   **无 2π 跳变**，FR_calf 转动也正常。多圈计数稳定，因此采用**软件 offset**，
   不做重新置零。FR_calf 的 +2.4427 属于当前稳定分支，offset +0.0285 自洽；
   更早的物理范围 [-4.50,-2.44] + 2π = [1.783, 3.843] 落在当前 offset 的
   clamp 范围 [1.60, 4.06] 内。若以后出现 2π 跳变，再考虑站立位置零。

### 8. 小 yaw 指令身体绕 z 晃动、大幅指令运动混乱（2026-11-03，待定位）

#### 现象

- 丢包问题基本解决后，推右摇杆（yaw_rate 指令）：
  - 水平轻推 → 身体轻微绕 z 轴晃动；
  - 大幅推 → 运动明显混乱。
- 一次失控后用户掐电；最后收到的状态（`/tmp/opendoge_status.json`）：

```text
state=damping_fault  fault="FL_hip_joint: feedback timeout"  can_tx=1620  can_rx=0
RL_thigh_joint   q=-2.7359   q_cmd=0.8000   dq=+42.61   tau≈0   temp=30   fault=1
```

#### 现场数据的正确读法

- `can_rx=0` 和 `FL_hip_joint: feedback timeout` 是**掐电之后**的必然结果，
  不是原始原因。
- `RL_thigh_joint` 才是失控瞬间的真实异常：`q=-2.7359` 比配置下限 `-0.785`
  低约 2 rad，`dq=+42.61 rad/s` 接近 EL05 上限 50。
  `fault` 字段是**状态帧**的 6 位故障信息（CAN-ID bit21:16，
  `kStatusFaultMask=0x3F`），其位定义与 0x3022 `faultSta` 寄存器不同：
  `bit0=欠压, bit1=三相电流故障, bit2=过温, bit3=磁编码, bit4=堵转, bit5=未标定`。
  因此 **`fault=1` 是欠压**，不是过流（过流是 2）；也可能只是掐电瞬间
  母线掉压留下的最后一帧。不能据此判断过流。
  这与“大腿被甩/别到限位外，控制器再用满 kp 拉回”吻合。
- 之前 `RL_calf`（9 号）在**站立时**反复丢包、趴伏时不丢；那是独立的
  角度/负载相关物理问题（线缆/接头/内部线/机械），不能靠软件参数掩盖。

#### 候选原因（按验证顺序）

1. ~~**IMU 轴向/符号**~~（2026-11-03 **已排除**）。
   训练侧 actor 用 `robot/imu_ang_vel`（机体坐标系）、`projected_gravity_b`；
   真机 `dm_imu_bridge.py` 默认 `--axis-map xyz --axis-signs 1,1,1`。
   实测：静止 `gz≈-1`；低头 `gx>0`、抬头 `gx<0`；右侧向下 `gy<0`；
   上方看逆时针偏航 `wz>0`。这与训练定义
   `projected_gravity_b = R^T·(0,0,-1)` 完全一致。
   （此前表中“低头 gx<0”是写错了，已更正。）**不要改 axis-signs。**
2. **关节 direction / 零位**。12 个 `direction` 在 2026-10-30 复核过，
   11-02 又在站立位重新置零；但 RL_thigh/RL_calf 反复异常，值得再单独确认
   一次（尤其失控后机械是否被顶坏、零位是否漂移）。
3. **RL_calf 站立丢包**。若反馈 stale/串用旧值，策略看到错误的关节状态，
   步态会突然不对称；yaw 尤其敏感。
4. **`base_lin_vel=zero`**。训练时该观测来自仿真真值；真机设为 0 属于
   分布外输入，可能降低整体稳定性（但不是 yaw 专属）。
5. **观测/动作契约**（已核对，暂列为排除项）：读取 LainLab 训练源码
   `mjlab.tasks.velocity.velocity_env_cfg` 与 `opendoge_flat.onnx` 元数据后确认：
   - actor 观测顺序、48 维、`last_action=raw action`、`action_scale=0.25`
     与部署一致；
   - 训练 `timestep=0.005`、`decimation=2` → 策略 100 Hz，部署
     `inference_hz=100` 一致；
   - flat 任务初始命令范围 vx ±0.8 / vy ±0.5 / yaw ±0.8，手柄

### 9. 悬空 RL 测试：松开摇杆后仍前后迈步，随后 RL_calf 丢包（2026-11-03）

#### 现象

- 机器人**悬空**，轻推左摇杆向前；最初几秒不动，之后出现剧烈、小幅度的
  前后迈步；用户此时已松开摇杆。
- 随后 `RL_calf_joint: feedback timeout` → `damping_fault`。

#### 日志分析

- 前 4 个快照：`ActiveRL`，12 个关节 `q≈q_cmd`、`dq≈0`、`|tau|<0.5 N·m`，
  `can_tx≈can_rx≈1320` —— 策略在**保持站位**，通讯正常。
- 第 5 个快照：所有腿 `dq` 突然变大（-6.3…+7.2 rad/s），
  `FL_calf` 和 `RR_calf` 的 `q_cmd` 同时被钳到上限 **-1.04**，
  而 `FR/RL` 小腿保持弯曲；髋部也是 FL/RR、FR/RL 成对动作。
  **这是标准的 trot 对角步态**，不是随机抽动。
- 此时机器人悬空：脚没有地面反力，同样的目标位置会让腿自由摆动，
  所以看起来"剧烈而小幅度"，力矩反而很小（<0.7 N·m）。
- 随后 RL_calf 连续丢帧超过 `state_timeout_s=0.1`，触发 `feedback timeout`；
  进入 damping 后 `can_rx` 又回到 1320，说明是**瞬态 burst**，不是持续掉线。
- `late_us` 大多 1–3 µs（只有故障后出现过一次 80 ms），**不是调度停顿**。
- 12 个关节 `fault=0`、温度 28–29 °C，没有过流/过温/欠压。

#### 结论

1. **悬空测试对 locomotion 策略是分布外**：训练/仿真里脚一直有地面接触，
   悬空时策略照常输出 trot，但腿没有接触约束，表现为快速空摆。
   不能据此判断策略在实地上是否稳定。
2. **RL_calf 的丢包是真实问题**：这次在**悬空、几乎无负载**的情况下，
   只要腿开始大幅摆动就丢包 —— 进一步指向**角度/线缆/接头/振动**，
   而不是“站立负载”本身。
3. **"松开摇杆后还在迈步"需要查命令值**：状态文本行不含 `vx`。
   要确认松杆后 `/tmp/opendoge_command.state` 的 `vx` 是否已归零
   （手柄漂移/死区），以及丢包期间策略是否看到了 stale 的 RL_calf。

### 11. 后腿 hip 失能不掉 + USB2CAN1 USB 链路反复抖动（2026-11-04）

#### 现象

- RL 运行时后腿（RL/RR hip）反馈丢失 → `DampingFault`；
- Ctrl-C 退出后这两个 hip 仍保持阻尼、无法失能；
- 再启动 `start_robot.sh policy` 报：

```text
✗ can0 vcan UP but only 1 bridge process(es), expected 2
... can1/can2/can3 同样
✗ Some services are not ready.
```

- 重新上电后重复，两个 hip 仍然不失能。

#### 现场证据

- `journalctl -k`：USB2CAN1（SOULDE `1483:1111`，Hub 的 `1-3.3` 口）
  在 18:26–18:32 反复 `USB disconnect` / 重新枚举（设备号 117→125），
  出现 `device not accepting address ... error -71`、
  `cdc_acm ... acm_start_wb ... failed: -19`；
- `opendoge-usb2can1.service` 连续失败 **71 次**，日志
  `/dev/USB2CAN1 not found after 20s`，直到 18:32:44 才恢复；
- USB2CAN0（`1483:1110`，`1-3.7` 口）同时间段稳定，`NRestarts=1`；
- `lsusb -t`：Bus1 Port3 是 7 口 Hub，同时挂 2×USB2CAN、手柄、摄像头、蓝牙；
- 下游设备声明总电流 800 mA（100+400+200+100），超过 USB 2.0 主机口
  500 mA；Hub 自身 `bmAttributes=0xE0`（声明 self-powered）。

#### 代码链路（为什么 hip 会一直硬）

1. `opendoge-vcan.service`（oneshot + `RemainAfterExit=yes`、
   `ExecStop=/bin/true`）先创建 `can0-can3` 并保持 UP，**即使对应 USB 模块不在**；
2. `usb2can_vcan_bridge.py` 只做 vcan↔USB 转发；USB 设备消失时进程退出，
   systemd 每 ~23 s 重试（ExecStartPre 等 20 s）；
3. 这期间 deploy 向 `can2/can3` 写帧仍然“成功”（vcan 接受写入，无 ACK），
   但帧到不了后腿电机；
4. 后腿电机（7–12，含 RL_hip=7、RR_hip=10）收不到新指令，保留最后一条
   阻尼指令；hip 承重最明显，所以看起来“两个 hip 不失能”；
5. Ctrl-C 的 `COMM_STOP` 同样只写进 vcan，bridge 不在 → 丢失；
6. EL05 `0x7028 canTimeout` 默认 **0（关闭）**，电机不会自己释放；
7. `verify_can` 用**全局** `pgrep -fc` 计数（expected=2）并在 4 个接口上
   重复打印，无法指出是 USB2CAN1/`/dev/USB2CAN1` 缺失；bridge 进程
   “活着但 fd 已死”（EIO 被吞掉）时还会假通过。

#### 结论

根因是 **USB2CAN1 的 USB 链路抖动**（端口/线缆/供电/模块），
不是 CAN 协议，也不是策略。后腿失能不掉是“bridge 死了 + 电机无失联看门狗”
的直接后果。`start_robot.sh` 拒绝启动是正确保护，只是提示信息误导。

#### 处理

- 硬件：给 Hub 接外部 5V 电源（≥2A）；USB2CAN1 换口/换线，与 USB2CAN0
  对调定位；`journalctl -k` 观察是否还 disconnect；
- 电机侧：deploy 启动时写 `0x7028 canTimeout`（RAM，1 s），bridge/deploy
  死掉时电机自动释放（修改 42）；
- 启动检查：按模块/设备检查 unit、`/dev/USB2CAN*`、进程 `--map`，
  并给 15 s 重枚举窗口（修改 43）；
- bridge：EIO/ENODEV 时设置 eof 并退出，发送失败不再静默（修改 44）；
- deploy：退出时按反馈新鲜度报告“无法确认失能”，不再假报成功；
  启动失败路径补发 COMM_STOP；fault clear 不再在 CAN 断链时假成功（修改 45）。

### 12. 开机时 USB2CAN 服务被 systemd 跳过（ordering cycle）（2026-11-04）

#### 现象

开机日志里能看到两个 USB2CAN 服务被“跳过/删除”：

```text
multi-user.target: Found ordering cycle on opendoge-usb2can1.service/start
multi-user.target: Job opendoge-usb2can1.service/start deleted to break ordering cycle
multi-user.target: Found ordering cycle on opendoge-usb2can0.service/start
multi-user.target: Job opendoge-usb2can0.service/start deleted to break ordering cycle
```

结果：开机后 `can0-can3` 的 vcan 在，但两个 bridge 不会自动启动；必须手动
`systemctl start opendoge-usb2can0 opendoge-usb2can1`。

#### 根因

**已安装**的 `/etc/systemd/system/opendoge-vcan.service` 还是旧版本：

```ini
After=multi-user.target
Wants=multi-user.target
```

而两个 bridge 单元是 `Wants/After=opendoge-vcan.service`、并且
`WantedBy=multi-user.target`；于是形成

```text
multi-user.target → usb2can → opendoge-vcan → multi-user.target
```

的依赖环，systemd 只能删除 bridge 的 start job 来破环。

仓库里的 `daemons/opendoge-vcan.service` 已经是修正版：

```ini
# Do not order after multi-user.target: ...
After=systemd-udevd.service
```

即**仓库是对的，机器上装的是旧 unit**。重装服务或手动改 unit 即可。

#### 处理

```bash
# 方式 A：重装（会重启 CAN/IMU/手柄服务，机器人空闲时做）
bash scripts/install_services.sh --vcan

# 方式 B：只改 vcan unit
sudo sed -i 's/^After=multi-user.target$/After=systemd-udevd.service/; /^Wants=multi-user.target$/d' \
  /etc/systemd/system/opendoge-vcan.service
sudo systemctl daemon-reload
sudo systemctl restart opendoge-vcan opendoge-usb2can0 opendoge-usb2can1

# 验证（不应再出现 ordering cycle）
systemd-analyze verify opendoge-usb2can0.service 2>&1 | grep -i cycle || echo OK
```

#### 延迟与实时性

- `late_us=12664`（12.7 ms）是**每秒统计窗口内的最大控制循环延迟**；
  damping 下无影响；偶发一次属于非实时 Linux 的正常调度抖动。
- 现在 `start_robot.sh` 默认 `REALTIME_ARGS="--realtime --cpu 0"`；
  `setcap cap_sys_nice+ep` 一次即可，但**每次 `colcon build` 重新链接二进制后
  会丢失**，需要重新执行；没有 cap 时 deploy 打印警告并按普通优先级运行。
- bridge/IMU/手柄单元在仓库里加了 `CPUAffinity`（bridge 2-3/4-5，
  IMU/手柄 6-7），避免和 deploy 的 CPU 0 抢核；需要重装或手动写进已安装 unit。

### 13. 迁移到赤乌（CHIWU）4×CAN 原生 SocketCAN（2026-11-05）

### 修改 8：新增 `hardware/motor/watch_angles.py`

**文件**：`hardware/motor/watch_angles.py`（新增）

**功能**：

- 只发 `COMM_READ_PARAM (0x11)`，**不使能、不运动、不改参数**；
- **默认逐电机顺序读**（`--mode sequential`，菜单同款最稳路径），
  每个电机 `mechPos` 无回包时最多重试 `--retries` 次（默认 3）；
- `--mode batch` 批量读（快），只对缺失 `mechPos` 的电机做补读，
  最后再补 `mechVel/faultSta`；
- 轮询 `mechPos (0x7019)`、`mechVel (0x701B)`、`faultSta (0x3022)`；
- 按 deploy 配置换算 `logical = direction × (mechPos/reduction − offset)`；
- 显示 `mechPos / logical / Δlogical / mechVel / faultSta`；
- 每轮打印 `replies=N/12`；
- 启动时检查 `canX` 状态、`usb2can_vcan_bridge.py` 进程（含 PID）、
  `/dev/USB2CAN*` 符号链接，并提示“本脚本不打开 USB2CAN”；
- `--once` 单次快照；`--csv` 记录手掰过程；`--rate-hz` 调频；
  `--ids` 只读指定电机；
- `--probe`：按 `--passes`（默认 2）多轮补扫，逐电机重试，
  打印**所有原始回包**（comm/motor/target/index/value/payload），
  最后给出每个电机的有效值和回包帧数。

**关于 n/a（重要）**：

EL05 是绝对编码器，`mechPos` 上电即可读，**不需要转一圈**。
显示 `n/a` 只表示这一轮没收到该电机的 type-17 回包。常见原因：

1. 电机没上电（读参数不需要使能，但需要供电）；
2. `usb2can_vcan_bridge.py` 没在跑，或对应 `canX` 没 UP；
3. 电机 ID 不是 1-12，或该 ID 不在对应总线上；
4. deploy 正在以 1000 Hz 占用总线，回包被挤掉；
5. USB2CAN 串口路径丢回包。实测桥接统计 `can->usb=30, usb->can=27`，
   约 10% 的读请求没有回包，所以要重试。

先用 `--probe --passes 3 --retries 3` 做多轮补扫；脚本默认已经是
**逐电机顺序读 + 重试**（`--mode sequential`，`--timeout 0.3`），
比批量稳。只有追求刷新率时才用 `--mode batch`。

**用法**：

```bash

sudo python3 hardware/motor/watch_angles.py --probe --passes 3 --retries 3 --timeout 0.5

# 实时观察（默认逐电机顺序读 + 重试）
sudo python3 hardware/motor/watch_angles.py

# 追求刷新率时用批量（丢包会自动补读）
sudo python3 hardware/motor/watch_angles.py --mode batch --rate-hz 5

# 只读一条腿
sudo python3 hardware/motor/watch_angles.py --ids 1,2,3

# 记录手掰过程
sudo python3 hardware/motor/watch_angles.py --csv /tmp/angles.csv --rate-hz 10
```

> `--sequential` / `--batch` 作为兼容别名保留；**默认就是顺序读**，
> 直接 `sudo python3 hardware/motor/watch_angles.py --rate-hz 2` 即可。

**验证手掰减速比**：手转小腿 ~0.2 rad，看 `ΔmechPos / Δ关节角`

**原因**：部署退出时只发 damping burst 然后关闭 CAN，**从不发 `COMM_STOP`**。

### 修改 36：修正 EL05 故障位名称（0x3022 与状态帧是两套位定义）（2026-11-03）

**文件**：`hardware/motor/el05_motor_menu.py`、
`hardware/motor/monitor_status.py`

**原因**：之前的分析把 `fault=1` 当成“过流”，但 EL05 手册里存在**两套不同的
故障位定义**，而且仓库里的 `FAULT_NAMES` 本身也把 0 和 2 写反了：

**A. 状态帧（type 2）的故障信息 = CAN-ID bit21:16**（手册控制演示章节）：

| 位 | 含义 |
|----|------|
| bit16 → 字段 bit0 | 欠压 |
| bit17 → bit1 | 三相电流故障 |
| bit18 → bit2 | 过温 |
| bit19 → bit3 | 磁编码故障 |
| bit20 → bit4 | 堵转过载 |
| bit21 → bit5 | 未标定 |

所以状态帧 `fault=1` 是**欠压**；过流是 `fault=2`。`deploy` 的
`safety.cpp` 只打印 `bitN`，没有名称，之前据此推断成了过流。

**B. 0x3022 `faultSta` 寄存器**（手册 §3.3.7）：

```text
bit0 过温   bit1 驱动芯片   bit2 欠压   bit3 过压
bit4 B相过流  bit5 C相过流  bit7 编码器未标定
bit8 硬件识别 bit9 位置初始化 bit14 堵转过载 bit16 A相过流
```

原 `el05_motor_menu.py::FAULT_NAMES` 把 `0` 写成“欠压”、`2` 写成“过温”，
正好与手册相反；`el05_usb2can_scan.py::FAULT_NAMES` 本来就是正确的
（`0:过温, 2:欠压`），可作为交叉验证。

**diff 1（`el05_motor_menu.py`，0x3022 名称）**：


### 修改 37：修正 sim2sim 的 projected_gravity 旋转方向（2026-11-03）

**文件**：`sim2sim/deploy_mujoco.py`

**原因**：训练侧 mjlab 的定义是

```python

```

其中 `root_link_quat_w` 是 MuJoCo `data.xquat`（**body→world**），
`quat_apply_inverse` 是 `R^T·v`。因此低头（绕 +y）时
`gx = +sinθ > 0`。

`deploy_mujoco.py` 的 `_rotate_vector_by_quat()` 实现的是**正向** `q·v·q⁻¹`
（`R·v`），却直接用它把世界重力转进机体系：

```python

    np.array([0.0, 0.0, -1.0]), quat)   # = R·g，不是 R^T·g
```

虽然直立时两者都得到 `(0,0,-1)`，但低头/横滚时 `gx/gy` 的符号会**整体翻反**。
这会让 sim2sim 的观测与训练/真机不一致。2026-11-03 实测真机 IMU
（低头 `gx>0`）与训练一致，反而说明是仿真侧写错了。

**diff**：

```diff
+    @staticmethod
+    def _rotate_vector_by_quat_inverse(v, q):
+        """q^-1 * v * q (即 R(q)^T·v)，与 mjlab quat_apply_inverse 一致。"""
+        w, x, y, z = q
+        t = 2.0 * np.array([y*v[2]-z*v[1], z*v[0]-x*v[2], x*v[1]-y*v[0]])
+        return v - w*t + np.array([
+            y*t[2]-z*t[1], z*t[0]-x*t[2], x*t[1]-y*t[0]])
...
-            imu.projected_gravity = self._rotate_vector_by_quat(
-                np.array([0.0, 0.0, -1.0]), quat)
+            imu.projected_gravity = self._rotate_vector_by_quat_inverse(
+                np.array([0.0, 0.0, -1.0]), quat)
```

**验证**：新函数与 mjlab venv 里的 `quat_apply_inverse` 数值一致：
低头 20° → `(+0.342, 0, -0.940)`；抬头 → `(-0.342, 0, -0.940)`。
用修正后的 sim2sim 重跑 `--mode rl --cmd 0 0 0.75 --lin-vel-mode zero`：

无 fault、峰值力矩 2.61 N·m（与修正前几乎相同，说明策略对这组符号不敏感，
但观测现在与训练一致）。

**影响**：只影响 sim2sim 观测，不影响真机（真机的
`dm_imu_bridge.py` 用 `quat_rotate_inverse`，方向本来就是对的）。

**回滚**：去掉 `_inverse` 调用，恢复 `_rotate_vector_by_quat`。

### 修改 39：新增 `el05_set_can_timeout.py`（电机侧失联保护）（2026-11-04）

**文件**：`hardware/motor/el05_set_can_timeout.py`（新增）

**原因**：用户反馈 Ctrl-C 退出 deploy 后，9 号电机有时仍保持阻尼。
deploy 退出时确实会发 3 次 `COMM_STOP`，但 9 号的 CAN 链路本身在丢包，
3 次全丢时电机就会保持最后一条阻尼指令。

EL05 有电机侧保护参数（手册 §3.3.6 / 可读写参数表）：

```text
0x7028 canTimeout  uint32  默认 0（关闭）
单位 50 µs：20000 = 1 s，10000 = 0.5 s，4000 = 0.2 s
非 0 时，电机在超过该时间没收到任何 CAN 指令后进入 reset 模式。
```

这样即使 COMM_STOP 丢失、deploy 崩溃或线缆断开，电机也会自己释放。

**工具用法**：

```bash
# 只读
sudo python3 hardware/motor/el05_set_can_timeout.py

# 先只给 9 号写 1 s，保存并读回
sudo python3 hardware/motor/el05_set_can_timeout.py --ids 9 --value 20000 --apply

# 恢复默认
sudo python3 hardware/motor/el05_set_can_timeout.py --ids 9 --value 0 --apply
```

写入流程：`COMM_WRITE_PARAM (0x12)` 写 0x7028 → `COMM_SAVE_PARAM (0x16)`
→ `READ_PARAM` 读回校验。默认只读，必须加 `--apply` 才写 Flash。

**建议**：先只改 9 号，确认 Ctrl-C 后能自动释放，再考虑 12 个电机统一
设成 10000（0.5 s）或 20000（1 s），避免单电机失联后仍出力。
设置后若行为没变，断电重启电机一次。

**验证**：`py_compile`、`--help` 通过；实际写入需要实机（尚未执行）。

**回滚**：`--value 0 --apply` 恢复关闭。

### 修改 53：一条总线写失败不再中断其他腿的阻尼（2026-11-05）

**文件**：`deploy/src/main.cpp`、`hardware/motor/el05_socketcan.hpp`

**现象**：某条腿丢包/总线出错后进入 DampingFault，但**其他腿没有立刻阻尼**，
而是继续按最后的 RL 目标动，直到电机 `0x7028 canTimeout`（1 s）才松开；
看起来像“身体倾斜后其他腿根据 IMU 继续原地走”。

**根因（代码）**：

1. `sendFrame()` 一旦 `write()` 失败就调用 `fail()`，把 `ok_` **永久**置 false；
2. 控制块用 `can_ready = can.ok()` 把**整块 12 关节发送**门控掉，之后再也不发；
3. 即使不看 `ok_`，循环里 `if (!can.sendMotion(...)) { ...; break; }` 会在
   **第一个失败关节**处 break，后面的关节（其他总线）也不发。

结果：一条总线出错 → 12 个电机都收不到新的阻尼帧 → 健康腿保持最后一条
`kp=12` 的 RL 目标 → 继续动；1 s 后 canTimeout 才让它 reset。IMU 在
DampingFault 下并不参与控制，所以不是“IMU 驱动它走”。

**修改**：

```cpp
// main.cpp 控制块
- const bool can_ready = !opt.dry_run && can.ok();
- if (can_ready) {
-   for (...) if (!can.sendMotion(...)) { fault_reason=...; break; }
- }
+ if (!opt.dry_run) {
+   bool any_write_failed = false; std::string first_write_error;
+   for (...) {
+     if (!can.sendMotion(...)) {
+       if (!any_write_failed) first_write_error = can.lastError();
+       any_write_failed = true;
+     }
+   }
+   if (any_write_failed) { fault_reason=first_write_error;
+                           runtime_state=DampingFault; }
+   else { can.clearError(); }
+ }
```

```cpp
// el05_socketcan.hpp
+ void clearError() { ok_ = true; last_error_.clear(); }
```

- 每个 tick **都尝试发全部 12 个关节**；一个总线失败只影响它自己的电机；
- 失败仍会进 DampingFault（安全），但健康总线立刻收到 damping；
- 全部写成功时 `clearError()` 恢复 `ok_`，修好总线后 `clear_fault` 才能生效。

会一直保留，导致此后永久误报（尤其在 ready/damping 这种本来就不关注跟踪的状态）。

**修改**：

```python
- gap_ms = j.get("max_gap_ms")
- if gap_ms is not None and int(gap_ms) > max_gap_ms:
-     flags.append("GAP")
+ # GAP 是“当前”条件；max_gap_ms 是 lifetime（含启动空窗），不能用于实时标志
+ current_gap_ms = j.get("status_age_ms")
+ if current_gap_ms is None:
+     current_gap_ms = age_ms
+ if current_gap_ms is not None and int(current_gap_ms) >= 0 and int(current_gap_ms) > max_gap_ms:
+     flags.append("GAP")
```

- `--max-gap-ms` 仍默认 12 ms，但含义改为“当前 type-2 status age 阈值”；
- `max_gap_ms/last_gap_ms` 继续保留在 status JSON 里作为历史参考；
- 新增测试：`max_gap_ms=400` 但 `status_age_ms=4` 时不报 GAP。

**验证**：

```text

→ lifetime max_gap does not raise GAP / All passed
```

**实机附注**：当时 `status` 文件已 62.7 s 未更新（deploy 已停止），所以 monitor
显示的是最后一次快照；同一快照里 4 路 CAN 都是 `ERROR-WARNING`（这是真实

**回滚**：把 GAP 改回 `max_gap_ms`（会重新出现启动空窗误报）。

### 修改 62：install_services.sh 在 sudo 下安装用户服务（2026-11-07）

**文件**：`scripts/install_services.sh`

**现象**：

  ```bash
  RUN_UID="$(id -u "${RUN_USER}")"
  RUN_HOME="$(getent passwd "${RUN_USER}" | cut -d: -f6)"

  ```

  ```bash
    XDG_RUNTIME_DIR="/run/user/${RUN_UID}" \
    DBUS_SESSION_BUS_ADDRESS="unix:path=/run/user/${RUN_UID}/bus" "$@"
  ```
  否则直接执行。
- 用户 unit 用 `run_user install -d/install -m 0644` 写到调用者家目录；
  `systemctl --user daemon-reload/enable/restart` 全部走 `run_user`。
- Step 4 前先 `loginctl enable-linger "${RUN_USER}"`，确保 `/run/user/<uid>`
  存在；`whoami` 改为 `RUN_USER`。
- CAN/xboxdrv 的 system 部分不变。

   ```python
       atomic_write(output, format_imu_state(...))
   ```

   - 读失败时保留上一帧，不新增 fault。

3. **状态可观测性**：`LoopStats` 增加
   `last_obs_imu_age_s`/`last_obs_joint_age_s`（不被 `resetWindow()` 清零），
   status JSON/终端新增 `obs_imu_age_ms`/`obs_joint_age_ms`，代表**最近一次
   策略观测实际使用的样本年龄**。原来的 `imu_age_ms` 仍是 200 Hz 安全轮询
   样本的年龄。

**为什么先不提高 control_hz**：

提高 `control_hz` 会让 `sendMotion` 和电机回包同比翻倍，并改变命令 EMA、
IMU debounce 的每秒执行次数；本修改先用“推理前刷新”把观测延迟的软件相位
去掉，CAN 负载和实时循环频率都不变，风险更小。如果 `obs_*_age_ms` 已降到
~0–5 ms 但 5.8 Hz yaw 仍在，再评估 `control_hz=250–400`（400 Hz 时每总线
约 30% 负载）或 action 低通/重训。
